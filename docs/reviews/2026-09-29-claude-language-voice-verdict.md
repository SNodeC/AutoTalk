## 1. Executive assessment (revised)

The reported bug is real and reproducible, and this pass shows it is **wider than my first verdict described**, with **two additional, independently confirmed entry points** to the same class of defect that my first proposed remedy would *not* have caught, plus **one overbroad claim in my first verdict that I must retract**: `add_version(translate=True)` — which I previously called "the existing correct pattern" — is itself not fully correct once deliberate per-slide language overrides are involved. 1. Talk settings → Narration language combo, explicit pick (LV1, first verdict, reconfirmed).

### LV12 — MEDIUM, Design limitation (not independently fixable without new state) — Whole-slide granularity of `narration_origin`
- **Governing invariant tension:** "no new parallel validity state/flags" vs. "must not silently erase deliberate slide-language or mixed-passage choices" — these two constraints are in genuine tension for a slide that mixes one explicit-tagged passage with one untagged passage.
- **Exact source:** `Slide` dataclass (project.py:181-196) has exactly one `narration_origin: str` field per slide; there is no per-`Passage` equivalent (`Passage` — project.py:48-51 — has only `text`/`language`, no origin/readiness field).
- **Evidence type: Executed + static.** Probe "Concern 2c" confirms a mixed slide really does parse into `["", "Chinese"]` (untagged, then explicit), and confirms by direct inspection of the dataclass that no finer-grained field exists to flag only the untagged half.
- **Recommendation, presented as an explicit tradeoff (not a proven defect) per the review's instructions:**
  - **Option A (permissive):** flag the whole slide as `"translation"` whenever it has *any* untagged passage (matches the general LV1/LV2/LV9/LV10/LV11 rule uniformly). Consequence: on Codex rewrite, the deliberately-tagged Chinese passage's *text* is protected only by the existing prompt instruction ("Preserve explicit [Language] paragraph markers…", services.py:151) — an LLM-compliance promise, not a structural guarantee — and its *audio* will be regenerated regardless (harmless — same content, just wasted computation, same category as LV13) because the whole-slide digest changed.
  - **Option B (conservative, smaller, zero risk to deliberate content):** exclude any slide that contains **at least one** explicit-tagged passage from automatic flagging at all (`and not any(p.language for p in slide.passages)` added to the predicate) — trading a known, narrower residual gap (the untagged portion of *mixed* slides only stays silently stale, exactly as today, and must be caught by the user via the existing "Rewrite slide text…" affordance) for an absolute guarantee that automatic flagging never touches a slide that has *any* deliberate tag in it.
  - **My recommendation:** **Option B**, because it is strictly smaller, never requires trusting LLM prompt compliance for correctness, and the owner's brief explicitly prioritizes "preserve intentional overrides" over completeness. This should be confirmed with the owner before implementation, since it is a genuine tradeoff, not a clear-cut fix.

### LV13 — LOW/MEDIUM, NEW — Switching a voice/speaker back to a previous value does not reuse an already-valid, on-disk WAV (efficiency, not correctness)
- **Evidence type: Executed**, framed carefully to avoid a blanket claim in either direction, per the user's explicit instruction.
- **What is true:** `speech_key()` is a pure function of content (project.py:383-394), so speaker A → B → A produces the **exact same key** for A both times, and `Project.audio_name()` derives the file path **from that key** (project.py:347-348) — so the original file for A is never overwritten by B's generation and remains valid, byte-for-byte, on disk. Probe "Concern 3" confirms this precisely: `recomputed key for speaker A after switching back == original key_A? True`; `target_path_for_A.is_file()` is `True`.
- **What is also true:** `ready()` (project.py:396-401) only trusts the single `slide.audio_key`/`slide.audio_file` pointer, which now points at B's file, so `ready()` is `False` immediately after switching back — even though a valid file for A already exists at the exact path `synthesize()` would target. `services.synthesize()` (services.py:247-283) never calls `.is_file()` on its computed `output` path before sending the request to the speech backend — confirmed by reading the full function, no such check exists.
- **Net effect:** **content correctness is never at risk** (no wrong audio could ever be served this way) — this is purely a missed caching opportunity, costing one redundant real-TTS call per toggle-back. I am explicitly not claiming this is a correctness bug, per the user's caution against a blanket claim.
- **Recommendation (design judgment, optional, not required for the language/voice correctness fix):** add a single `output.is_file()` short-circuit in `synthesize()` before building the request for a given item, when `not force`. Estimated cost: **+2 to +4 lines**, isolated to `services.py`, with no interaction with the language-fix work in §4. I would treat this as a separate, optional efficiency improvement rather than part of the core remedy, since it is not required to satisfy any of the stated fixed invariants.

### LV14 — Correction / honest limitation, NEW — The first verdict's proposed "generic mismatch warning" for an already-mislabelled saved talk cannot detect the coordinator's actual case; explicit, user-directed recovery proposed instead
- **What I claimed before:** "a generic 'state-mismatch' notice... if `text_ready==True`, `audio_file` exists, and `ready()==False`."
- **Why it is wrong, demonstrated by execution:** the coordinator's actual inspected talk had **already been resynthesized once** under the wrong language before inspection — i.e. the bad Start had already completed a full cycle, and `synthesize()`'s completion handler (services.py:298-306) had already **re-stamped `slide.audio_key`/`audio_file`/`audio_sha256`/`duration` to match the (wrong-language) `speech_key()` exactly**. Probe "Concern 6" reproduces this precisely: after simulating one completed (buggy) resynthesis cycle, `text_ready == True` **and** `ready() == True` **simultaneously**, with `audio_key == speech_key()` — structurally indistinguishable from a genuinely correct, fully-prepared slide. There is **no field in the current data model** that records "this slide's language was ever silently changed without translation" once the digest has re-converged.
- **Honest conclusion:** AutoTalk **cannot safely, automatically detect** this specific already-corrupted state without either (a) reading and understanding the actual language of the narration text — explicitly forbidden ("without guessing language") — or (b) adding new persistent provenance state solely to detect a historical mistake, which the brief explicitly discourages ("no new parallel validity state/flags/cache authorities merely to patch counters"). **I withdraw the generic-warning proposal entirely.**
- **What going forward, and what for already-affected talks:**
  - **Going forward:** the LV1/LV2/LV9/LV10/LV11 fix in §4 prevents this state from being created in the first place (the `narration_origin` flip happens *before* any resynthesis, not after), so no talk fixed after this change and edited only through the app can reach this state again.
  - **For a talk already in this state (like the coordinator's):** the only honest path is **explicit, user-directed recovery through existing operations**, because the user is the only party who actually knows the content's true intended language. Concretely: **Talk → "Rewrite all talk text…"** (ui.py:627, bound to `create_narration(rewrite=True)`, app.py:603-616) — this **already exists**, requires **zero new code**, and already shows an explicit confirmation naming the version before acting: *"Rewrite all included slides in {version.name or language}? This replaces your edits in that language version."* (app.py:609-610). The equivalent per-slide action, "Rewrite slide text…" (app.py:836-845), offers the same protection at finer granularity, with its own confirmation naming the target language (app.py:840). Neither needs new UI, new detection heuristics, or any language-guessing — they simply need to be the thing the user reaches for once they notice (by ear, or by reviewing the text pane) that a talk sounds or reads wrong. I recommend documenting this explicitly (e.g. in the app's own help/tooltip text near the language field, a one-line pointer such as "If existing narration is in the wrong language after changing it here, use Talk → Rewrite all talk text…") rather than attempting automatic detection.

### LV15 — LOW, Design judgment, NEW — Streaming mid-generation settings changes are silently dropped with no user-visible notice

## 4. Coherent minimal remedy plan (revised)

**Principle, unchanged:** reuse the existing `narration_origin == "translation"` authority end-to-end. **What's new this pass:** the remedy needs one additional primitive (a before/after effective-language diff, not a presence check) and one additional mechanism (pin-on-first-content) to cover LV9/LV10 without opening a Cancel-safety hole in the Application-scope dialog.

1. **New shared predicate** (project.py, ~3 lines): `def _needs_translation(slide): return any(p.language == "" for p in slide.passages)` (or, if Option B from LV12 is adopted: `and not any(p.language for p in slide.passages)` guard added at each call site, not inside the predicate itself, to keep the predicate reusable for both permissive and conservative use).
2. **Diff-based invalidation, reused for LV1/LV2/LV9(part)/LV10** (project.py, ~15-20 lines): inside `Project.set_setting`'s `language` handling — both the talk-scope branch (project.py:254-258) and the generic slide-scope fallthrough (project.py:259) — compute each affected slide's `self.setting("language", slide)` **before** mutating, apply the mutation, then compute it again **after**; only where the two differ **and** `_needs_translation(slide)` **and** `narration_origin != "translation"`, set `narration_origin = "translation"`. This single change covers the explicit-set direction (LV1/LV2) **and** the inherit/revert direction (LV10) for free, since both already funnel through this one function.
3. **Pin-on-first-content, for LV9** (project.py + 2 one-line call sites, ~8-10 lines total): a small `Project` method, called from `app.py:357` (manual edit) and from `services.apply_narration` at services.py:167 (Codex-generated text), that — only when `self.version.language == ""` and the slide's passages just became non-empty — sets `self.version.language = self.setting("language")` (crystallizing whatever is *currently* effective, app-default or not) and `self.version.name` accordingly. This closes LV9 structurally, without touching `apply_defaults()` at all, and therefore **without needing any new Cancel-safety mechanism** for the Application-scope dialog (which today has no project-level undo snapshot — confirmed by reading `SettingsDialog.done`, settings.py:140-170, scope-0 branch touches only `w.defaults`/`w.screen`, never `w.project`).
4. **`add_version(translate=True)` fix, for LV11** (project.py, net ~0 lines — one line changed from unconditional to guarded): reuse the same predicate from step 1 so only slides with inherited-language content get `narration_origin = "translation"`; slides with all-explicit-tagged passages keep their natural default.
5. **Authority unification, for LV4** (project.py/app.py, net ≈ −4 lines): delete `Project.language`'s independent setter logic; have it and `app.py:1057` delegate to `set_setting`.
6. **Do not** add anything to `apply_defaults()`, `SettingsDialog.done()`, or any new field/flag — steps 1–5 are entirely reuses/reshapes of `narration_origin`, `Project.setting()`'s existing precedence, and the existing `add_version` call, as required.

**Revised net line-growth estimate:** approximately **+35 to +50 lines**, essentially all in `project.py`, plus two one-line call-site additions in `app.py` and `services.py`. This is a meaningful upward revision from my first verdict's "+25 to +35" — that earlier estimate did not yet account for the before/after diffing needed to correctly skip deliberate overrides (concern 2a), the pin-on-first-content mechanism needed for LV9, or the `add_version` predicate fix for LV11. I consider this revised range accurate to within the review's precision, not final line-by-line accounting.

**Explicit tradeoff requiring an owner decision before implementation:** LV12's Option A vs. Option B (whole-slide flagging permissiveness for slides mixing tagged and untagged passages). I recommend Option B.

**Optional, independent, not required for correctness:** LV13's `output.is_file()` short-circuit in `synthesize()` (+2 to +4 lines) — a separate, smaller, unrelated change the owner may or may not want bundled.

**Already-mislabelled saved talks (revised per LV14):** no automatic detection or rewriting, of any kind, is proposed — the coordinator's inspected case is provably undetectable by any structural signal available today, and inventing one would mean either guessing language content (forbidden) or adding new persistent state purely to flag a historical mistake (discouraged). The only proposed action is a **documentation/UI-copy nudge** pointing at the **already-existing** "Talk → Rewrite all talk text…" and per-slide "Rewrite slide text…" commands as the explicit, user-confirmed recovery path — zero production code growth beyond a possible tooltip sentence.

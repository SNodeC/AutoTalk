## 0. Executive verdict and evidence scope

**Verdict:** the application's data and process layer (`Project`, `Playback`, `SpeechSession`, cache-key derivation, migration) is sound enough that a rewrite is not justified. The UI-state layer built on top of it (`MainWindow.refresh()`, `MainWindow.load_settings()`, `SettingsPanel.load()`, `SectionDialog.sync()`) has real, reproducible defects — most importantly, a genuinely common operation (reading a conference URL, or any of several equivalent "create/prepare" actions) leaves several Talk-settings controls disabled until the user happens to navigate elsewhere in Settings and back. That defect, plus the still-unimplemented three-way settings-dialog split the owner has already decided on, are the two highest-priority items in this review. Several other reported issues (GPU retention, Realtime startup latency) could not be reproduced with the tools available to this review and are reported as explicit hypotheses, not verified findings.

**Method and evidence levels used throughout this report:**
- **Verified — reproduced:** a targeted pytest probe against the real classes (headless Qt, Xvfb) observed the exact claimed behavior. Four such probes were run: (A) a synthetic job whose success callback is `MainWindow.adopt`, confirming the general disabled-settings mechanism; (B) the same scenario driven through the **actual, unmodified** `MainWindow.read_conference()` method with only the single network+Codex call (`extract_scope`) faked — the closest reproduction of the owner's literal reported trigger achievable without live network/Codex access; (C) a recorded, synthetic-audio presentation stopped mid-flight to observe reachable widget states during the automatic post-recording export job; (D) a live render of the ordinary editor view with real narration text, screenshotted and interrogated for widget visibility/enabled state.
- **Verified — code trace:** the mechanism is unambiguous from reading the source (e.g., a specific line logs a value before a stripping step that exists three lines later, or a specific method never calls another method that owns re-enabling). No probe was written; none was needed to be confident, but this is a lower bar than (A)–(D) and is labeled as such everywhere it applies.
- **Reported, not reproduced — hypothesis:** the owner's report is plausible and I give the most likely code-level explanation, but I did not confirm it live (no GPU/Codex/screen-recording-device access was used in this review).
- **Design judgment:** a factual, verified observation where whether it constitutes a "problem" is a product decision, not something the code or the brief settles unambiguously.

**Full test suite:** `.venv/bin/pytest` under Xvfb with the native Qt/Breeze bundle — **325 tests passed in 59.09 s**, 0 skips, across 21 test files (4,320 lines) covering GPU-lifecycle edge cases, scoped-settings inheritance, legacy project migration, cancellation, recording recovery, and more. This suite was not re-run for this final pass since nothing in the reviewed snapshot changed; it is cited as standing evidence of baseline correctness for the paths it covers, alongside the probes above, which specifically covered paths the suite does **not** currently assert on (see §5).

**Explicitly out of scope for this review, stated once here rather than repeated per finding:** no real GPU inference, no real Codex/ChatGPT session, no real screen-recording device, no Windows/macOS execution, no terminal-level `SIGINT` delivery to a live process. Every finding that would require one of these to fully confirm is labeled "hypothesis" and not asserted as settled.

A small number of factual/methodological corrections were identified and folded into this final text before it was finalized (in particular around exact widget-reachability claims, click-cost counting, and the scope of a couple of findings); those corrections are reflected directly in the findings below rather than narrated separately.

## 1. Code quality and architecture

### 1.1 Bounded strengths, each tied to the specific code that earns it

- **`Project` is the single settings-resolution authority.** `Project.setting()`/`set_setting()` (`project.py:237-259`) implement slide → talk → application precedence in one place, used identically by the UI (`MainWindow.setting_value`), by synthesis request construction (`services.speech_config`), and by cache-key computation (`Project.speech_key`). This claim is bounded to the resolution logic itself — it does **not** extend to the UI layer that decides when those settings are *editable*, which is a separate, less disciplined system (see §5, F1).
- **Cache validity is derived, not flagged.** `Project.speech_key()` (`project.py:383-394`) hashes every effective input that determines an audio artifact's correctness (passages, voice identity/reference, resolved delivery instructions, sampling, trailing pause) into one digest; `Project.ready()` (`project.py:396-401`) compares the slide's stored key against a freshly computed one and checks the file exists. There is no separate "is this stale" boolean anywhere to drift out of sync with reality — this is a genuinely good design choice.
- **`Playback` is the single timeline authority.** Position, buffering, capture, and audio-format negotiation all live in one class (`playback.py`); `MainWindow` never touches sample-accurate timing directly. Verified by reading every audio-touching code path in `app.py`; I found none that bypasses `Playback`.
- **`SpeechSession` is the single GPU-process owner.** One class (`runtime.py:414-593`) with a lock (`guard`) and explicit `phase`/`retention` state; every caller — preview, whole-talk preparation, Realtime workflow, manual load — goes through the same `speech_session()` context manager. No second speech-process implementation exists anywhere in the tree.
- **Migration and integrity checking are more careful than most desktop apps bother with.** `Project.load()` (`project.py:460-549`) handles schema versions 1–4 explicitly and recomputes legacy audio-cache keys rather than trusting stored ones; `Project.validate()` (`project.py:551-597`) re-hashes the source PDF, every slide's stored audio, every voice reference, every imported clip, and the background track on load, refusing to trust a manifest whose files moved or changed underneath it. **This is not a blanket claim about every asset**: `validate()`'s check for rendered slide-image PNGs is presence-only (`if not self.image(slide).is_file(): raise …`, `project.py:582-583`) — there is no stored hash for slide images and no `Slide` field to hold one. Given slide images are machine-rendered at import time and not normally hand-edited afterward, this is best read as a **possible consistency tradeoff between six asset classes that are otherwise hashed and one that isn't**, not automatically a defect requiring a new stored field — but it is worth naming precisely rather than folded into an "everything is hashed" generalization, which would be inaccurate.
- **Cooperative cancellation is consistent.** `Task.check()`/`Cancelled` (`runtime.py:51-66`) is threaded through every long operation in `services.py`, `codex.py`, and `runtime.py`, and `Job` (`app.py:36-61`) translates it uniformly at the UI boundary. I did not find a long-running operation that ignores cancellation.
- **Platform/process handling is unglamorous but correct.** `runtime.py` distinguishes frozen-launcher library search paths, Windows `taskkill` vs. POSIX process-group signaling, and strips inherited `LD_LIBRARY_PATH`/`PYTHONPATH` before spawning Codex/`uv`/speech children.

None of the above is a claim that the application has no correctness gaps — it is a claim about five specific, well-bounded subsystems. The gaps below live almost entirely in the layer *on top of* these subsystems, which is exactly the distinction the brief asked for: shared, well-factored code in one module is evidence about that module, not a substitute for checking the layer that consumes it.

### 1.2 Architecture and maintainability concerns

- **The "is this control editable" question has three independent, non-communicating owners**, and this is the direct architectural cause of the highest-severity UI finding in this review (F1, §5). `MainWindow.refresh()` (`app.py:474-638`) computes a correct, complete `editable = job is None and not transport.active and presentation is None and not recorder.source` and applies it to most main-window widgets. `SectionDialog.sync()` (`ui.py:233-256`) receives that same `editable` value from its caller and applies it at section granularity inside the shared Settings dialog. But `SettingsPanel.load()` (`options.py:178-231`) **independently** computes a narrower, different condition — `widget.setEnabled(w.job is None)` (`options.py:208`) — for every leaf field it owns (tolerance, mode, pause, after-slide, background gain/loop, and several others), omitting the `transport.active`/`presentation`/`recorder.source` terms entirely. `SettingsPanel.load()` is invoked, among other places, from inside a `Job.succeeded` callback (`MainWindow.adopt`/`accept_result`) — which Qt fires **before** `Job.finished` clears `self.job` — so it reliably disables those fields at the moment almost any ordinary operation completes, and nothing calls it again afterward to undo that. The bug is a direct, mechanical consequence of having three places decide one thing.
- **`MainWindow.refresh()` at ~165 lines and `MainWindow.load_settings()`/`SettingsPanel.load()` at a further ~80 combined lines constitute the majority of the app's "what is the UI allowed to do right now" logic, and they are not the same function.** This is the single biggest maintainability risk in the codebase: it is easy to add a new widget, wire it into one of these three functions, and silently miss that it needs the same treatment in another — which is precisely what happened here.
- **No exception safety around capture finalization.** `Playback.stop()` (`playback.py:389-399`) calls `self._finalize_capture()` with no `try/except`; `ScreenCapture.close()` (`screen_capture.py:178-179`) explicitly raises if a recording device thread does not join within its 3-second timeout. If that raises, `Playback.stop()` returns before reaching `self.state = "stopped"`, and nothing in `MainWindow.stop_presentation()` (`app.py:832-840`) guards against it either. I did not force a real device stall to confirm this end-to-end (no recording hardware access in this review), so this remains a **hypothesis**, not a verified finding — but it is a real, named gap in error handling exactly where the brief asks the review to look, and the mechanism (an unguarded call whose failure path is never exercised by the test suite) is verified.
- **No `SIGINT` handler is installed anywhere.** `main()` (`app.py:1506-1523`) never calls `signal.signal(...)`. This is **verified statically** — the absence of any signal-handling code is unambiguous from a full-repository search. What is **not** verified is *why* this produces the reported "Ctrl+C does nothing" symptom in practice; the most likely explanation (PySide6's slot-exception boundary printing and discarding the `KeyboardInterrupt` that Python's default handler would eventually raise, rather than it propagating out of `app.exec()`) is a plausible, standard PyQt/PySide pitfall, but confirming it — and confirming any fix actually produces clean shutdown of the speech subprocess, Codex subprocess, and any active recording — requires sending a real signal to a live, terminal-launched instance, which this review's tools do not support. A one-line handler that merely calls `QApplication.quit()` would be **actively insufficient**: `quit()` only requests the event loop to exit and does not invoke `MainWindow.closeEvent()` (`app.py:1466-1503`), which is where job cancellation, recorder shutdown, `speech.release()`, and project save actually happen — a naive fix would very plausibly leave the speech/Codex child processes orphaned, since they are deliberately started in their own process group (`start_process()`, `runtime.py:96-105`) specifically so a terminal's Ctrl+C does not reach them directly. Any fix needs to route through the existing `close()`/`closeEvent()` path, and needs a real-process test (send `SIGINT`, confirm process exit, confirm `pgrep` shows no orphaned children, confirm the saved project file is still valid JSON) before it can be called done.
- **Duplication is otherwise well controlled.** I did not find parallel implementations of settings resolution, audio mixing, or speech-process management. Several apparent duplications (toolbar mode/duration controls mirrored in the Settings dialog; three separate entry points for manual GPU load/unload) are genuinely the same handler wired to multiple controls, not competing implementations — this is a legitimate, low-risk convenience pattern, not an architectural problem.

## 2. Whole UI/UX review

### 2.1 What is demonstrably working well

- **Palette/style handling is real, not just documented.** `MainWindow.event()` (`app.py:224-231`) explicitly re-polishes the stylesheet on `ApplicationPaletteChange`, handling live light/dark switches; the shared stylesheet (`ui.py:23-47`) only sets spacing/radius/palette-relative colors, with no hardcoded colors and no forced-dark override anywhere in the current tree.
- **Settings-dialog entry points route directly to the correct page, not through a generic landing screen.** Every "…settings" button/menu item in the app calls `show_section(section, scope, focus=...)` (e.g., `w.talk_action`, `w.voice_button`, `w.presentation_button`, the status-bar engine button, "Language options…") with the target section and scope named explicitly, and `show_section` switches both the navigation list and the scope combo synchronously before the dialog is shown. In practice this means **most Settings-routed controls are one click to reach**, not two — a materially better result than assuming "open dialog, then find the section" as a two-step process would suggest. This is a genuine strength I want to be specific about crediting, since it is easy to undercount by treating "opens a dialog" as automatically a multi-step journey.
- **Cache-driven readiness language is trustworthy.** Status text like "Needs text," "Audio needs updating," "Audio ready · 0:23" (`app.py:588,592`) is computed from the same `Project.ready()` boolean used to gate playback — the UI cannot claim something is ready when the underlying cache check disagrees, because it is literally the same function call.
- **Whole-talk preparation is not hidden behind Start.** "Create talk text"/"Create talk audio" sit directly above the editor, always visible when a talk is open (`ui.py:589-591`), independent of the Start button — this matches the brief's explicit requirement.
- **Recording discoverability matches the roadmap's own stated fix.** The record checkbox is in the always-visible summary/footer area across editor, Quick, and presenter views (`ui.py:745-747`), not buried below a scroll boundary.

### 2.2 What is not: the two verified defects that most affect ordinary use

- **F1 (settings staying disabled) — see §5 for full detail.** Reproduced through the actual, unmodified "Read conference website" code path with only the network+Codex call faked, and separately through the general mechanism (any operation whose success callback is `adopt`/`accept_result`, which covers most "create/prepare" actions). This is High severity because it is common (not an edge case) and because its symptom — a handful of fields greyed out while adjacent fields on the same page stay editable — looks exactly like a rendering bug rather than a state-management one, making it hard for an ordinary user to work around by anything other than accident.
- **F4 (settings scope selector) — see §5.** The application ships one Settings dialog with a "Settings for" combo box at the top (`ui.py:174-178`), documented as correct in `USER_GUIDE.md:90`. The owner has already made the required decision — three separate windows (**Application defaults**, **Talk settings — [title]**, **Slide settings — [number]**), no in-dialog scope combo — and the project's own `ROADMAP.md` records this as an explicit, still-open, unimplemented requirement. This is not a design question this review is reopening; it is a placement defect against an already-decided requirement, and the current shared-panel implementation (`SettingsPanel`, field registry tagged by `scopes=(...)`) is in a reasonable position to support the split without duplicating field logic three times, since the underlying resolution/editor code is already shared. The high-frequency slide-level controls that are currently **inline** in the editor sidebar (inclusion, after-slide, timing budget, delivery override — `ui.py`'s "This slide" panel) are worth keeping exactly where they are as fast-path shortcuts once the third dialog exists for the remaining, less-common slide settings (clip management, slide-scoped voice/language) — that is an implementation detail of satisfying the decision, not a reason to question it.

### 2.3 Findings that are real but are not "the whole UI is bad"

- **F10 — Two primary-styled buttons are simultaneously visible and enabled in the ordinary editor screen.** Rendered and confirmed live: the toolbar's "Prepare and start" and the editor's "Create slide audio" are both `primary=True`, both visible, both enabled, on the same screen, at the same time, whenever a talk with usable narration is open. This is a **verified visual fact**, not an inference. Whether it is *confusing* — as opposed to a defensible way of marking "the two most useful buttons on this screen," given they operate at genuinely different scopes (whole-talk vs. single-slide) — is a **design judgment**, and the brief asks for a sensible hierarchy, not a literal one-primary-button-per-window rule. My own view: I would demote "Create slide audio" to a non-primary style, since a user's eye is drawn to blue-highlighted controls first, and having two on screen dilutes rather than reinforces the "the one big thing to do here" signal a primary button is supposed to send — but I want to be clear this is a recommendation grounded in a verified fact, not a rule violation.
- **F3 (revised framing) — the interaction around Start while an automatic post-recording export is running lacks clear feedback, and I could not fully confirm its downstream consequence.** What I directly observed, before the probe was terminated: during the automatic export job that follows stopping a recorded presentation, the mode selector, File actions, and every narration-authoring control are correctly locked (`editable=False`); the Start button itself remains enabled and clickable; clicking it does not error, it sets `self.after_job = self.start_mode` and shows the status message *"Presentation will start after the current operation finishes."* After the export job cleared, the mode selector was still observed disabled, which is **consistent with** a new presentation having already begun (since `record_presentation` was still on for that project) — but my probe hung shortly after that observation and had to be terminated before I could directly assert that a second recording had, in fact, started. I am stating this precisely rather than either overclaiming a confirmed bug or dropping the observation: **clicking Start during a save is a request the user made**, and queuing it is defensible behavior, not automatically a "functional bug" or an "unrequested recording" — the legitimate critique is narrower: the status message does not tell the user that recording will resume automatically as part of that queued restart, and a control that stays fully interactive-looking during what otherwise reads as a locked screen is an easy target for an impatient or accidental click. That is a feedback-clarity and accidental-activation risk, worth addressing, and distinct from a claim that the software does something the user didn't ask for.

## 3. Startup timing, progress, and improvement options

**No live GPU/Codex measurement was performed in this review.** Everything below is either a critical-path trace of the code (verified) or a citation of the project's own prior, self-described "individual sample" measurements (historical, explicitly not re-measured by this review).

**Traced critical path for Realtime with an already-warm, matching speech model** (`workflow()`, `services.py:365-415`):
1. Model re-acquisition is started on a background thread concurrently with narration planning (`ThreadPoolExecutor`, `services.py:373-374`) — this genuinely implements "load speech concurrently with Codex." If the model is already loaded and its configuration matches, `SpeechSession.__enter__` returns almost immediately (`runtime.py:441-443`), so **a warm, matching model is not the bottleneck** in this path.
2. Because no narration exists yet at Realtime start, a **mandatory, whole-deck** Codex call runs first: *"Plan this complete talk. Write FINAL natural spoken narration for slide {opening}; use short outlines in the other slides' narration fields"* (`services.py:149-151`). The request payload (`narration_result()`, `services.py:129-160`) includes every included slide's source text and page image, not just the opening slide's — the prompt size and the model's reasoning load scale with deck size.
3. Only after that call returns does audio synthesis for slide 1 begin.

**Historical measurements (all on small, two-slide German decks — stated explicitly by the source document itself):**

| Source | Deck size | Warm first audio | Codex planning component | Total prepare |
|---|---|---:|---:|---:|
| `VERIFICATION.md:766-770` | 2 slides | **15.48 s** | 14.95 s | 34.78 s |
| `VERIFICATION.md:807-809` | 2 slides | **16.42 s** | dominant, same call | 41.07 s (46.36 s end-to-end vs. 30 s target) |
| `VERIFICATION.md:759-765` | 2 slides | 43.03 s (cold-ish; model load 35.55 s) | 14.33 s, overlapped | 84.15 s incl. MP4 save |

Read at face value, both genuinely *warm* two-slide runs land inside or at the edge of a 15–20 s target, and in both cases essentially the entire budget is consumed by the whole-deck Codex planning call, leaving near-zero margin. **The owner's own screenshot of the reported slow-startup complaint shows a 24-slide deck** ("Slide 1 of 24"). None of the measurements above are on a deck of that size, and I have no basis — measured or otherwise — to claim the two-slide timings generalize to 24 slides. Given the outline prompt's payload scales with slide count, it is a structurally plausible (not confirmed) explanation that a 24-slide deck's whole-deck planning call alone could consume most or all of a 15–20 s budget by itself, independent of any GPU/model factor.

**Improvement options, presented as options to weigh rather than a recommended fix:**
- **Baseline-measure first.** Before changing anything, measure a same-shape (~24-slide), warm-model, real-Codex Realtime start and separate Codex-planning time from model/synthesis time using the instrumentation already in place (`runtime.py`/`app.py` `measurement` events, which are genuinely stage-separated and not timer-based estimates — verified in code). Without this, any implementation choice is guesswork.
- **Option: a lighter "opening-only" Realtime prompt that skips full-deck planning for slide 1.** This would very likely reduce first-audio latency, especially for large decks, but it has a real product cost: the current `"ahead"` outline call exists specifically to give the model a whole-deck plan (consistent time-budget allocation, narrative arc, pacing) before any slide is finalized; writing slide 1 blind to the rest of the deck sacrifices that coherence. Whether that tradeoff is acceptable is a product decision this review can surface but should not make unilaterally, and it should not be adopted before the baseline measurement above establishes whether the planning call is actually the dominant cost at the reported deck size.
- **Progress reporting is already reasonably good and does not need to be part of this tradeoff.** `backend_loading_progress()` (`runtime.py:382-411`) parses real vLLM log lines into named stages with measured counts where available and falls back to stage-name-only (no invented percentage) otherwise; `job_event()`'s progress handling (`app.py:929-940`) never synthesizes a percentage from elapsed time. This satisfies the "no invented percentages, explain unmeasurable stages" requirement as written, verified by reading the code paths involved.

**GPU retention ("the model keeps unloading") — reported, not reproduced, no live GPU access used.** Default retention is genuinely `"session"` ("Never — keep loaded until I close AutoTalk"), and I found no code path that silently overrides that choice with an automatic idle-unload. The one policy-independent reload path is `SpeechSession.configure()` (`runtime.py:523-529`): any difference in backend/model/source/sampling between two operations forces a full process kill-and-restart regardless of the selected retention policy — correct behavior (a genuinely different configuration needs a different process) that could still look like "unloading" to a user switching voice sources or toggling advanced sampling between operations. Establishing the real trigger needs logging of `SpeechSession.matches()` mismatches during an actual affected session, which is outstanding.

## 4. Button visuals and interaction conventions

- **Ellipsis usage is correct almost everywhere, and I verified this against the connected handler, not just the label text.** File/save dialogs, `QInputDialog`s, and Settings-section openers consistently carry "…"; immediate actions consistently don't. One example worth citing for its precision: the editor's per-slide text button's label itself changes with the same conditional logic that decides whether its handler shows a confirmation dialog — `"Create slide text"` (no confirmation needed, no ellipsis) vs. `"Rewrite slide text…"` (confirms via `QMessageBox.question`, ellipsis present) vs. `"Translate slide text"` (no confirmation, no ellipsis) — all three driven by one handler (`regenerate_slide()`, `app.py:1045-1054`) and one condition (`slide.passages`/`narration_origin`). This is a well-executed detail, not an accident.
- One borderline case: **"Check for model updates…"** runs a background job and then reports its result via `QMessageBox.information` — it uses ellipsis for a control that *reports* rather than *collects input*, a non-standard but defensible reading of the convention. Low priority.
- **Chevron/disclosure convention is the clearest, most consistent gap in the app.** Every expandable section — "Advanced Realtime buffering," "Advanced recording," "Output quality," "Timing," "Delivery," "More vocal attributes" — is built by one shared helper, `disclosure()` (`ui.py:108-115`), as a plain checkable `QPushButton` with no chevron/arrow glyph at all; the shared stylesheet defines no `QPushButton:checked` rule, leaving native pressed-state rendering as the only expanded/collapsed cue. This is uniform across every instance (a consistent violation, at least, not six different ones), and mechanically simple to fix by giving the shared helper an explicit direction indicator instead of relying solely on native checked-state styling.
- **A second, different disclosure idiom coexists with the first.** "Show AI notes"/"Hide AI notes" swaps its own label text rather than using a chevron (`ui.py:633-636`) — a defensible, common convention on its own (comparable to "Show password"), but it means the app currently has two different ways of saying "click here to reveal more," neither of which is the chevron the brief asks for.
- **Primary-button hierarchy is mostly disciplined but not universal — see F10 (§2.3, §5).** The brief asks for a *sensible* hierarchy, not literally one primary action across an entire window; two coexisting primary buttons in the editor is a verified fact, and whether it reads as confusing is a judgment call I've given, not a rule violation to cite.
- **Checkbox recognizability is resolved.** The shared stylesheet (`ui.py:36-37`) only sizes the native `QCheckBox`/indicator; there is no custom asset and no forced-dark override anywhere in the current tree, matching the project's own claimed fix.
- **Numeric alignment / minimum-size layout is handled centrally, not per-widget.** A global `QFormLayout` field-growth/row-wrap policy and a global 32 px minimum control height are applied once across the whole app (`ui.py:864-869`) rather than fixed ad hoc per screen — a sound approach, though the specific claim that this holds up at 150% scaling on every screen is inherited from the project's own prior verification record and was not independently re-rendered at that scale in this review.

**Closing assessment:** preserve the current architecture and continue refining it rather than rebuilding; the strongest evidence for that is that every high-severity finding in this review (F1, F4) is a defect in a thin, identifiable layer (Settings-dialog state management and shell structure) sitting on top of data/process modules that are, within the bounds actually verified here, sound.
